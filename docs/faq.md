# 常见问题

> 每条都给出"怎么自己验证"，而不是只给结论。

---

### Q1. 我改了数据库，为什么微信排行榜没变？

因为排行榜读的是**服务端**，不是你的手机。链路是：

```
本地库 → Provider → App 读取 → App 上报 → 平台服务端 → 排行榜
```

本地改动只能影响前三跳。App 什么时候上报、平台什么时候刷新，都不由手机决定。

**验证方法**：改完之后，把本地改回去（或还原备份），过一会儿再看排行榜——
如果排行榜还是新值，说明它确实来自服务端。

---

### Q2. 为什么"今天步数"看起来比实际走的少？

两个常见原因：

1. **还没落库**：服务按 `Delay`（默认 300 秒）批量写库，走在路上时数字是滞后的。
2. **App 显示的是它自己算的数**：小米健康有自己的 Realm/MMKV 缓存，不一定等于 Provider 的值。

**验证方法**：

```bash
adb shell dumpsys miui_step_counter_service | grep 'Today Total'
adb shell cmd miui_step_counter_service trim-all     # 强制落库
```

再对比 App 里的数字。

---

### Q3. `trim-all` 是"上传"吗？

不是。【实测】它只把**内存缓存写进本地数据库**，不联网、不碰服务端。
"上传"发生在 App 侧（微信/小米健康各自有上报节奏）。

---

### Q4. 为什么 root 反而读不了 Provider？

因为 Provider 校验的是**权限**（`miui.permission.READ_STEPS`），不是 uid。
root 的进程并没有被授予这个签名级权限，所以照样 `SecurityException`。

**能读的方式**：
- `dumpsys miui_step_counter_service`（无需权限，能看今日总量与逐段历史）
- 有 root 时直接读 `Steps.db`
- 白名单 App 内部查询

---

### Q5. 数据库里一段只有几十步，正常吗？

正常。`Record Delay` 默认 30 秒，也就是**每 30 秒一段**；一段 40~80 步属于常见范围。

---

### Q6. 排行榜上同一个人出现两次，是什么原因？

实测排除了"多设备"：微信运动「数据来源」里只有一个「我的手机」。
更可能的两种：

1. **封面卡片 + 榜单首项**重复渲染（上榜者同时出现在封面区和列表第 1 名）；
2. 客户端列表合并时的重复项。

**验证方法**：退出重进排行榜，看重复项是否还在；若消失，属于渲染问题。

---

### Q7. 步数什么时候清零？

【社区】次日 0 点清零，当日榜单约 22 点锁定。
【实测】跨过 0 点后，`Today Total` 确实从 0 重新开始。

---

### Q8. 改了本地数据，会不会影响手机其他功能？

不会。它只涉及一个数据库文件（`Steps.db`），不涉及系统分区、服务配置或其他 App 的数据。
可能被间接影响的是**读取这个库的 App**（小米健康、微信、支付宝、QQ），
以及展示步数的界面（负一屏卡片等）。

---

### Q9. 换机型 / 升级系统后还能用吗？

私有 cmd 接口与数据库结构**都可能变化**。换环境后先跑：

```bash
python scripts/diagnose.py
adb shell cmd miui_step_counter_service --help
```

对比本文档的命令表与字段，确认一致后再谈其他。

---

### Q10. 有没有现成的开源工具做这些？

检索结果（截至 2026-11）：

| 平台 | 结果 |
|---|---|
| npm | 无相关包（搜 `miui steps` / `stepcounter` / `xiaomi health` 均为前端组件） |
| GitHub | 只有只读可视化项目（如 `miui-step-viewer`），未见封装私有 cmd 接口的 |
| 酷安 | 以 Xposed 改步数为主，未见"立即同步"类工具 |
| 小米官方文档 | 只写 Provider 的 URI/列名，未提 cmd 接口 |

所以本仓库的价值主要在于**把这条链路和接口记录下来**，而不是提供一个工具。
